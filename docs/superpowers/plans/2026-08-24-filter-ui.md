# Filter UI Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Put the five filters — name, status, branch, generation, country — in front of the user
on both the Family Tree and Members pages, backed by the URL so a filtered view is linkable, and
show the branch and generation the server already derives.

**Architecture:** One shared module, `features/filters/`, holds the state hook and both
presentations. Filter state lives in the **URL query string**, not component state: a filtered
view is then linkable, survives a refresh, and the export button (Plan 4) builds its download URL
by passing the same parameters through instead of re-deriving them. Above the breakpoint the five
controls sit in an inline bar; below it they collapse into a sheet behind one **Filters** button
carrying an active-count badge, so a user is never filtered without being told.

**Tech Stack:** React 19 + TanStack Query, react-router `useSearchParams`, react-i18next,
vitest + Testing Library. No new dependencies.

**Spec:** `docs/superpowers/specs/2026-08-24-member-data-filters-export-design.md`

This is **Plan 3 of 4** from the spec's §9 decomposition. Plans 1 (member contact data) and 2
(derivation and the shared filtered query) are complete on this branch — read their STATUS blocks
and `git log --oneline main..HEAD` before starting, and do not re-run them. Plan 4 (Excel export)
depends on `useMemberFilters` producing the query string it will append `.xlsx` to.

**Everything the server needs already exists.** No endpoint, contract, or migration changes here.
If a step seems to need one, stop: something has gone wrong.

Section references of the form §N point at the design spec above, or — where the text says
"specification §N" — at the source requirement document it implements.

## Global Constraints

- Branch: `member-data-filters-export`, already cut from `main`. Do not create another branch.
- Every new user-facing string must be added to **both** `frontend/src/i18n/locales/en.json` and `ar.json`. `locales.test.ts` enforces key parity and will fail the suite otherwise.
- Test framework is fixed: vitest 4 + Testing Library. Do not add test packages.
- Arabic test fixtures use real Arabic names (`سليمان`, `داوود`), matching existing tests.
- **No new CSS file and no CSS framework.** The codebase styles with inline `CSSProperties`
  objects against the tokens in `index.css` (`var(--surface)`, `var(--space-4)`, …). Follow it.
- Reuse `SearchableSelect` for the branch and country pickers. It already folds Latin accents,
  Arabic hamza/ة/ى spellings and Arabic-Indic digits before matching, and portals its list so a
  scrolling container cannot clip it.
- Reuse `useDebouncedValue` for the search box. Every keystroke would otherwise be a request and
  a recursive CTE.
- Filters are guarded by nothing new: a user who can see a page can filter it (spec §1.4).

### Refinement of spec §6.2

Spec §6.2 says the sheet appears "below `COMPACT_MAX_WIDTH`" and that this "reuses the existing
`useIsCompact` breakpoint rather than introducing a second one."

**Neither exists.** There is no `useIsCompact`, no `COMPACT_MAX_WIDTH`, and no `@media` rule
anywhere in `frontend/src` except a `prefers-reduced-motion` block. The spec was written against
an intention, not against the code.

**Resolution:** Task 2 creates them — one hook, one constant, in `features/filters/`. The spec's
actual requirement (one breakpoint, not two) is honoured; only the claim that it already existed
was wrong. `COMPACT_MAX_WIDTH` is **720px**: five controls at their natural widths plus a Reset
button need roughly 680px, and 720 leaves the page's own padding.

### Refinement of spec §1.2 — how "root-relative" is computed

Spec §1.2 moves two display sites to root-relative numbering: the member detail panel and the
search-hit subtitle. It justifies this by "the two schemes differ by exactly one", which is true
of *this* data — one parentless member — and not of the rule.

**Resolution:** do not subtract one. Derive the offset from the view being rendered:

```ts
rootRelative(node.generation, rootGenerationOf(view.rootMembers))
```

`rootGenerationOf` reads the absolute generation of the first root member the server returned.
That is correct with no root selected (داوود, absolute 1 → relative 0) and stays correct the day
a root picker is added, where subtracting one would silently be wrong.

The search-hit subtitle takes the same offset, because both sit on the same page and must agree.

### What keeps its absolute numbering

Untouched by this plan, per spec §1.2: the reports page, the PDF export's caption, and
`FamilyTreeNodeResponse.Generation` itself. They are tree-wide and have no selected root. Only
the two display sites named above change.

## Task 1: `useMemberFilters` — filter state in the URL

The one place filter state lives. `filterParams.ts` (Plan 2) already does the serialisation and
is unit-tested; this is the React binding over it.

**Files:**
- Create: `frontend/src/features/filters/useMemberFilters.ts`
- Test: `frontend/src/features/filters/useMemberFilters.test.tsx`

**Interfaces:**
- Consumes: `useSearchParams`, `toFilterParams`, `fromSearchParams`, `activeFilterCount`.
- Produces: `useMemberFilters() -> { filters, activeCount, setFilter, reset }` where
  `setFilter<K extends keyof MemberFilters>(key: K, value: MemberFilters[K] | undefined)`.
  Used by Tasks 5 and 6.

- [x] **Step 1: Write the failing test**

Render the hook inside a `MemoryRouter` and assert:

- With no query string, `filters` is `{}` and `activeCount` is 0.
- `setFilter('status', 'alive')` puts `?status=alive` in the URL and nothing else.
- `setFilter('status', undefined)` removes it again.
- Setting one filter preserves the others, and preserves a parameter the module does not own —
  `?memberId=` is already in TreePage's URL contract and a filter change must not drop it.
- `reset()` clears every filter **and keeps** `memberId`. `setSearchParams({})` as spec §6.1
  literally suggests would also clear the selected member, closing the user's panel as a side
  effect of pressing Reset Filters.
- `activeCount` counts narrowing filters only — `rootId` is not one.
- Two `setFilter` calls in one tick both land. Reading the current filters out of a stale render
  and writing them back wholesale loses the first.

- [x] **Step 2: Implement the hook**

`setFilter` and `reset` both go through the functional form of `setSearchParams`, so they compose
within a tick. Both use `replace: true`: a filter keystroke is not a navigation, and pushing one
history entry per character would make Back unusable.

Preserve unknown parameters by starting from the current `URLSearchParams`, deleting only the
keys `toFilterParams` owns, and re-adding what the new filter set produces.

- [x] **Step 3: Run the tests** — `npm test -- --run src/features/filters` passes.
- [x] **Step 4: Commit** — `feat: keep the member filters in the URL`

## Task 3: `FilterBar` — the five controls

Presentation only: it takes filters and callbacks and renders. Both pages and both layouts use
this same component, so the controls cannot drift between them.

**Files:**
- Create: `frontend/src/features/filters/FilterBar.tsx`
- Test: `frontend/src/features/filters/FilterBar.test.tsx`

**Interfaces:**
- Consumes: `useBranchesQuery`, `useGenerationsQuery`, `useCountriesQuery`, `SearchableSelect`,
  `useDebouncedValue`, `flagEmoji`.
- Produces: `<FilterBar filters activeCount onChange onReset layout="inline" | "stacked" />`.
  Used by Tasks 4, 5 and 6.

- [x] **Step 1: Write the failing test**

- All five controls render, each with an accessible name.
- Choosing a status calls `onChange('status', 'deceased')`.
- Choosing the branch and country options calls `onChange` with the id, and choosing the empty
  row calls it with `undefined` — clearing a filter must be possible without reloading the page.
- The generation select offers what `useGenerationsQuery` returned, labelled by number, **root
  first**: option `0` reads as the root's label, not as "0".
- Typing in the search box does not call `onChange` on every keystroke — one call after the
  debounce settles. Assert with fake timers.
- The search box shows the filter's current value on mount, so a linked URL arrives with the box
  filled in rather than empty over filtered results.
- Reset is disabled at `activeCount === 0` and calls `onReset` otherwise. A live Reset button
  over an unfiltered list is a control that does nothing.
- `layout="stacked"` renders the same controls full-width; `layout="inline"` renders them in a
  row. Assert one structural difference, not the CSS.

- [x] **Step 2: Implement**

Branch and country use `SearchableSelect` — 239 countries, and a branch list that will grow.
Status and generation use native `<select>`: three and ten options respectively, where a search
box is friction rather than help.

Country options carry `flagEmoji(code)` in the label and the ISO code plus dial code as
`keywords`, matching how `ContactFields` already builds them.

The search input holds its own draft state and pushes the debounced value up. Do **not** drive it
from the filter prop on every render: the URL round-trip lags the keystroke by the debounce
interval, and feeding it back would fight the cursor.

- [x] **Step 3: Run the tests** — passes.
- [x] **Step 4: Commit** — `feat: add the shared member filter bar`

**Files:**
- Modify: `frontend/src/features/members/MembersPage.tsx`
- Test: `frontend/src/features/members/MembersPage.test.tsx` (extend)

**Interfaces:**
- Consumes: `useMemberFilters`, `FilterControls`, `useMembersQuery(filters)`.

- [x] **Step 1: Write the failing test**

- The filter controls render above the table.
- Choosing a status refetches: assert `membersApi.list` was called with `{ status: 'deceased' }`.
- The table gains **Country** and **Branch** columns (spec §6.4). The root member's branch cell
  reads the "Root" label, not blank — specification §21.
- A country cell shows the flag and the localised country name, and reads as a dash when the
  member has none.

- **Full Name still composes from the lineage** after filtering. `fullName`/`lineageName` walk

  member whose father was filtered out must not lose their father's name from the display.

- [x] **Step 2: Wire the page**

`useMembersQuery(filters)`. The lineage index is the trap: build it from an **unfiltered**
members query, or compose the name server-side. Prefer the former — one extra cached query
against a 351-row endpoint, against a name that quietly changes as the user filters.

Add the two columns, reading `branchName` and `countryCode` off `FamilyMemberListItem`. The
country's display name comes from `useCountriesQuery` in the active language, as `ContactFields`
already resolves it; `countryCode` alone gives the flag.

## Task 6: The Family Tree page

The tree already dims non-matches for its own client-side text search. The server's `matches`
flag joins that same path rather than opening a second one.

**Files:**
- Modify: `frontend/src/features/tree/flattenTree.ts`
- Modify: `frontend/src/features/tree/TreePage.tsx`
- Modify: `frontend/src/features/tree/TreeCanvas.tsx`
- Test: `frontend/src/features/tree/flattenTree.test.ts` (extend)
- Test: `frontend/src/features/tree/TreePage.test.tsx` (extend)

**Interfaces:**
- Consumes: `useMemberFilters`, `FilterControls`, `useTreeQuery(filters)`.

- [ ] **Step 1: Write the failing test**

In `flattenTree.test.ts`:

- A node with `matches: false` produces a row with `dimmed: true`.
- With no filter every node has `matches: true`, so nothing dims — the existing rows are
  unchanged.
- The client's text-search dimming and the server's filter dimming **compose**: a row dims if
  either says so. Two independent reasons to fade must not overwrite one another.

In `TreePage.test.tsx`:

- The filter controls render, and choosing one calls `membersApi.tree` with that filter.
- A dimmed row is not selectable: clicking it opens no panel. Spec §4.2 says non-matches are
  "dimmed and non-selectable", and a panel for a member who is not in the result is a dead end
  the user has to close.
- A dimmed row is still **expandable** — it is only there to hold up a matching descendant, and
  disabling its expander would hide the match.

- [ ] **Step 2: Implement**

`flattenTree` reads `node.matches` and ORs it into `dimmed`. `TreeRow` keeps one `dimmed` field:
the canvas already renders it, and a second flag would need a second rendering rule for a
visually identical state.

`TreeCanvas` skips `onSelect` for a dimmed row and marks it `aria-disabled`.

- [ ] **Step 3: Run the tests** — passes.
- [ ] **Step 4: Commit** — `feat: filter the tree, dimming the ancestors of a match`

## What this plan does not do

- No Excel export, no download button, no ClosedXML — all Plan 4.
- No root picker. `rootId` stays in the URL contract and in `MemberFilters`, unset by the UI;
  `rootGenerationOf` is written so adding one later needs no arithmetic changed.
- No change to the reports page or the PDF caption's generation numbering (spec §1.2).
- No pagination, and no server change of any kind.
